## 0. 结论速览

**核心漏环节一句话：SF 里所有白点值（`sdrWhitePointNits` / `displayBrightnessNits`、层 `whitePointNits` / `dimmingRatio`）都是"渲染计划值"，它的物理兑现唯一通道是把 `displayBrightness`（0-1 档位）经 `composer HAL setDisplayBrightness` 变成真实背光抬升；本机这条通道存在断点嫌疑（HAL 无 `Capability::BRIGHTNESS`），同时 framework 兜底通道（`LogicalLight` LED 背光）是否被启用取决于 `mForceSurfaceControl` 的真实取值——而事实链对该值的推断需要纠错（见 §1.1）。计划值与物理背光一旦脱节，HDR 层按虚高的白点编码、SDR 层按虚高的 dimming 压暗，净效果 = 过曝，程度正比于 ratio，最高亮度 ratio→1 时失配消失——与实测症状完全吻合。**

本次审查**纠正了任务书事实链中的一处推断错误**：本地 smali 中 `mForceSurfaceControl = hasQuirk("canSetBrightnessViaHwc")`，**没有取反**（§1.1）。该值的真实取值直接决定走 SF 五参路径还是 LogicalLight 路径，是后续采样的第一优先判据（`dumpsys display` 里 BacklightAdapter 的 toString 可直接读出，见 §4 决策表 D1）。

**纠错（重要）**：`LocalDisplayAdapter$LocalDisplayDevice.smali` 行 2880-2885：
```smali
const-string v1, "canSetBrightnessViaHwc"
invoke-virtual {v0, v1}, DisplayDeviceConfig;->hasQuirk(Ljava/lang/String;)Z
move-result v0
invoke-virtual {p0, v0}, BacklightAdapter;->setForceSurfaceControl(Z)V
```
`move-result` 后**直传、无任何取反指令**。即本机逻辑是 `mForceSurfaceControl = hasQuirk("canSetBrightnessViaHwc")`，**而非事实链所写的 `!hasQuirk(...)=true`**。AOSP 原文（android16-release LocalDisplayAdapter.java，由 smali 反推核对）同构。这意味着：
- 若本机 display-device-config.xml **没有** `canSetBrightnessViaHwc` quirk（事实链的前提成立）→ `mForceSurfaceControl=false` → 结合 `mUseSurfaceControlBrightness=false`（HWC 不声明 BRIGHTNESS → SF `getDisplayBrightnessSupport=false`）→ **setBacklight 走 LogicalLight，背光由标准 LED/backlight 节点驱动，SF 白点五参从不发出**。
- 该情形下 SF composition state 的白点默认 `-1`（见 §2.5 gui::DisplayBrightness 默认值），dumpsys 里本不该出现有效的 whitePointNits/dimmingRatio——**与"SF dumpsys 实测 whitePointNits=sdr×ratio、dimmingRatio=1/ratio"矛盾**。矛盾的解释候选：① 实际有 quirk（force=true）；② 有第三方（vendor DPC 定制 / growhdr 模块注入）直接调 `SurfaceControl.setDisplayBrightness` 五参；③ nitsCapture 实测的"双参数"其实是 `LocalDisplayAdapter.handleHdrSdrNitsChanged(nits, sdrNits)`（LocalDisplayAdapter.java:1047-1053，参数恰为 (displayNits, sdrNits)，且仅当设备配置了 `sdrHdrRatioMap` 才存在）而非 SF 的白点。
- **裁决判据（零成本）**：`dumpsys display` 中 BacklightAdapter 自带 toString：`"BacklightAdapter [useSurfaceControl=... (force_anyway? ...), backlight=...]"`（smali 行 168-209）。`backlight=非null` 即 LogicalLight 在手；`useSurfaceControl/force_anyway` 直接读出两个布尔。

## 3. ② "过曝 ∝ ratio" 的源码解释候选（按证据强度排序）

**候选 1（主嫌）★★★：背光"计划-执行"断链** —— SF/HAL 通道（A2 → path A → composer3 SetDisplayBrightness）在无 `Capability::BRIGHTNESS` 的老 HWC 上被拒或被 vendor 静默忽略（HWComposer.cpp:871-890 只做错误码映射；高通 HAL 对不支持命令返回 UNSUPPORTED 属常见行为），同时 LogicalLight 兜底通道因 `mForceSurfaceControl` 取值而未启用（§1.1 纠错后此为待裁决项）。计划白点 755、物理峰值 542，失配量 = 755/542 - 1 = ratio - 1，**过曝程度严格正比 ratio**；HDR 高光被钳切 + SDR 压暗无补偿，双重贡献。最高亮度 ratio→1 → 失配消失 → 最轻。
支持证据：官方文档确认 HWC 无硬件 dimming 时须 defer GPU（mixed-sdr-hdr）；Dolby 官方承认 GPU-based 设备上此类亮度管理"没有解决方案"；本机 HWC 无 BRIGHTNESS 是已确认事实。

**候选 2 ★★：sdrNits 标定虚高** —— 542 若高于面板真实 SDR 白点（backlight→nits spline 标定偏差），则：dimmingRatio=542/755 偏轻（SDR 没压够）+ HDR 目标 755 偏高 → HDR 相对更亮。过曝同样 ∝ ratio。与候选 1 可叠加。采样：光测面板真实白点 vs 542。

**候选 3 ★★：fp16_client_target flag 链失效导致 ratio 未参与编码** —— `getHdrSdrRatio(buffer)` 的四前提（flag / FP16 buffer / EXTENDED / dispNits≥0）任一不满足即返回 1.0（Output.cpp:1818-1826），此时 `targetLuminanceNits = clientTargetBrightness × 755` 不做除法，client target 仍按 755 白点编码而物理背光不动 → 系统性偏亮。flag 状态可 dumpsys 读取（P3）。

**候选 4 ★（历史，已被 tx1008 缓解）：HWC 合成时 per-layer setBrightness 静默失败** —— OutputLayer.cpp:690-704，失败仅 ALOGE。强制 GPU 合成前闪烁/异常的成分；当前仍过曝说明主因不在（或不止）这里。

**候选 5 ★：App 侧 desiredHdrHeadroom 叠加** —— `Layer::setDesiredHdrSdrRatio`（Layer.cpp:1069-1080）存入层状态；分支 2 中 DISPLAY_HDR FP16 层在 `fp16_client_target` 关闭或层非 FP16 时 whitePointNits=sdr×currentHdrSdrRatio（App 期望）与系统 ratio 形成双系数。Android 15 语义：App desired 是"期望"，系统 ratio（deviceHeadroom）是硬上限（分支 1 的 idealized=min(...)、分支 2 的 clamp 均体现"系统 clamp App"）。若 growhdr App 同时设了 per-layer headroom，需排查双重放大。采样：dumpsys 每层 desiredHdrSdrRatio。

**候选 6 ★：HLG 层未受 begone_bright_hlg 钳制** —— 分支 1 若 flag 关，HLG 视频层 idealizedMaxHeadroom=满 deviceHeadroom → whitePointNits=755 全额提亮。仅影响 HLG 内容。

| D1: useSurfaceControl=false / force_anyway=false / backlight 非 null，且 D3 背光**有**抬 | 白点经 LogicalLight 背光正常兑现，过曝来自**标定虚高**（候选 2） | hook `DisplayDeviceConfig.getNitsFromBacklight`（或修 spline 标定值），把 542 校准到光测真实白点；growhdr 侧同步压低 spline30(sdrNits) |
| D1: 走 LogicalLight，但 dumpsys SF 仍有白点 | 第三方直调了 SF binder（候选：vendor DPC/growhdr 注入），物理背光与 SF 白点**各走各** | 先定位调用方（D4），统一收口到 `SurfaceControl.setDisplayBrightness` 静态方法的 hook（签名全拦），把 `displayBrightnessNits` 钳到物理可达白点 |

### 4.3 hook 点速查（全部在 system_server 进程，可被现有模块框架触达）

1. `com.android.server.display.LocalDisplayAdapter$BacklightAdapter.setBacklight(FFFF)` —— 参数裁剪的总闸（p2=sdrNits、p4=displayNits 直接可改；分支走向由 mUseSC/mForceSC 两布尔控制）。
2. `LocalDisplayAdapter$LocalDisplayDevice` 对 `DisplayDeviceConfig.hasQuirk("canSetBrightnessViaHwc")` 的返回值 —— 控制 force 分支。
3. `android.view.SurfaceControl.setDisplayBrightness`（F/F four overloads）—— 五参收口点（若走 SF 通道，这里是白点进 SF 前的最后关卡；也用于拦截第三方直调）。
4. `DisplayDeviceConfig.getNitsFromBacklight` —— 标定纠偏（候选 2 的修点）。
5. `LocalDisplayAdapter.handleHdrSdrNitsChanged(nits, sdrNits)` —— 系统 ratio 广播源（若 D7 有 sdrHdrRatioMap，这里是 ratio 的出生点，钳这里最上游）。
6. SF 进程内部（OutputLayer/RenderEngine）**不可**用 system_server hook 触达——所有修复必须在 framework 侧发起端完成；SF 侧白点是 binder 的被动接受方。
