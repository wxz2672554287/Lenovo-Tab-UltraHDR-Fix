## 二、审查清单逐项结论

### 1. 落地验证 —— 见上表,全部 PASS ✓

### 2. 并发/生命周期:LaunchedEffect 执行时机 —— 语义正确,重建重跑可接受 ✓

- `LaunchedEffect(Unit)` 位于 `if (!accepted) EulaScreen else { … }` 的 else 分支:EULA 接受瞬间 accepted false→true,组合树切换,effect **首次进入组合恰好执行一次**——"装完即建"语义达成(EULA 接受后立即,不必等用户进日志页)。
- 同一组合驻留期间的重复重组**不会**重启 effect(key=Unit 不变且 effect 未离开组合)——Compose remember/Effect 标准语义。
- Activity 重建(旋转/深色模式/进程内配置变更)→ setContent 全新组合 → effect 再跑一次。全部操作幂等(`mkdir -p`/`touch`/`chmod`/`cp -f`),代价仅 4~6 个 su 进程串行(每个约 30-80ms,IO 线程后台执行,用户无感)。**可接受**。
- HorizontalPager 的 LogsPage 离开页面即销毁、滑回重新组合 → 再跑一次 refresh+sync,同样幂等一致。
- 细节:effect 内阻塞代码(`waitFor`)不响应协程取消,Activity 销毁时线程会滞留到 su 返回为止——该机 su 无被动弹窗、快速返回,实际无影响。

### 3. root 阻塞 —— 该机定论下无 ANR、低阻塞风险 ✓

- `hasRoot()` 走 `LaunchedEffect → withContext(Dispatchers.IO)`,Main 线程零阻塞,**无 ANR 可能**。
- 关键事实:背景定论 SukiSU **无被动弹窗**(需用户在管理器主动授权)→ 未授权时 `su("id")` 立即被拒返回,已授权时立即成功——**"授权框挂起 IO 协程"的场景在该机不存在**。MainActivity.kt:55-57 注释宣称的"this is the moment the manager's grant dialog appears"与该定论相反(见问题清单 J1)。
- `syncLogToSdcard` 的 cp 用普通 su(非 suTimed)**合理**:日志文件日常几十~几百 KB,本地 cp 毫秒级;cp 的 stderr 输出远达不到 64KB 管道阻塞阈值;真正的大输出 `logcat -d`(MB 级)已按 B6 改用 suTimed(20s)。普通 su 无超时的理论挂起仅在其他 KernelSU 变体改变弹窗策略时成立(见 J2)。

### 4. 同步语义:refresh"先读后 cp" —— 顺序无影响,语义正确 ✓

推演:LogsPage.refresh 的 UI 内容来自 `Props.readLog()`(:70),其读取序为 **/data/system 优先(LOG_PATH_FALLBACK 权威源)**;`syncLogToSdcard`(:74)只是把同一权威源镜像到 sdcard 供文件管理器查看,**UI 从不读 sdcard**。因此:

- 不存在"本次刷新显示旧 sdcard"的问题——显示的根本不是 sdcard;
- cp 完成后 sdcard 与 /data/system 一致,镜像语义成立;
- readLog 与 cp 之间模块若新增 1-2 行,sdcard 会比 UI 多显示一两行,无关紧要;
- 先 cp 再读只是调换两个互不依赖的观察者顺序,结果等价。**现顺序正确,无需改**。

### 5. clearLog 后 sdcard 残留 —— 无此问题 ✓

LogsPage.kt:105-106 的清空**同时 truncate 两个路径**(`clearLog(Props.LOG_PATH)` + `clearLog(Props.LOG_PATH_FALLBACK)`),sdcard 侧当场清零,不等到下次 refresh 的 cp。truncate 原地清空(不 rm)也保住了 system_server 的 O_APPEND 写口。无残留。

### 6. 错误路径:hasRoot=false 时 MainActivity 静默跳过 —— 有兜底,够 ✓

- 未授权时首帧 effect 整体跳过(不产生 N 个注定失败的 su 调用,合理);StatusPage 是 pager 默认首页,root 状态行(105-111)直接显示"打开 SukiSU/KernelSU 管理器给本应用授权后重进"——用户装完打开 App 第一眼即可见,引导闭环成立("授权后重进"→ 重进时 effect 再跑 → 目录建成 + 首同步)。
- 残余小缺口见 J4:未授权时进日志页会 Toast"log_repair_fail",文案未区分"无 root"与"修复失败"。

### 7. Kotlin 语法/导入/尾逗号 —— 编译级 PASS ✓

MainActivity 的全限定名(`androidx.compose.runtime.LaunchedEffect`/`kotlinx.coroutines.withContext`/`Dispatchers`)不需要 import,合法;StatusState 构造尾逗号 Kotlin 1.4+ 合法;HdrRatioFix.java:94 全限定 AtomicBoolean 合法。release APK(今日 06:30)成功产出即最强证明。

## 四、结论

**通过,可发版。** 用户需求"装完即建日志目录 + 日志统一到 /storage/emulated/0/hdr日志/"落地完整且机制正确:

1. **装完即建**:EULA 接受后首帧 effect 异步完成 root 探测 → 目录预建(mkdir -p + 666)→ 主日志文件缺失自愈(touch+chown+chmod+restorecon)→ 首次 cp 同步,IO 线程执行零 UI 阻塞;
2. **统一可见**:镜像权威源(/data/system)到 sdcard,首帧 + 每次日志刷新双时机保活"常驻最新";UI 显示/导出仍锚定权威源(v2.0.7 B3 语义),镜像只服务文件管理器查看——分层正确;
3. **与 SELinux 定论一致**:模块侧零改动(不尝试写 /storage),sdcard 全靠 App root cp,单命令无 shell 元字符,符合该机 su 重组 argv 的约束;
4. **无致命/重要问题**,6 项建议均不阻塞发版,J1(注释与定论矛盾)建议下版顺手修掉以免误导后续迭代。
