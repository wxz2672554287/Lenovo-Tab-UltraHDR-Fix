## ② AOSP 上下文（引入版本 / 用途 / 消费点 / 默认值）

### flag 定义

- [surfaceflinger_flags.aconfig（main 分支）](https://android.googlesource.com/platform/frameworks/native/+/main/services/surfaceflinger/surfaceflinger_flags.aconfig)：`fp16_client_target`，namespace `core_graphics`，描述 "Controls whether we render to fp16 client targets"，bug `236745178`，`is_fixed_read_only: true`（默认关闭）。
- 版本形态差异（源码比对结论）：

| 分支 | 形态 | 该 prop 是否有效 |
|---|---|---|
| android13-release | 无此 flag | 无效（无任何消费点） |
| android14-release | 无此 flag（FlagManager 无该条目） | 无效 |
| android15-release | `FLAG_MANAGER_READ_ONLY_FLAG(fp16_client_target, "debug.sf.fp16_client_target")`（[FlagManager.cpp:235](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/android15-release/services/surfaceflinger/common/FlagManager.cpp)） | 有效 |
| main（Android 16） | `FLAG_MANAGER_ACONFIG_FLAG(fp16_client_target, "debug.sf.fp16_client_target")` | 有效 |

- 即：**该 prop 只在 Android 15 及以上存在**。Android 14/13 上设置它完全无效（无害也无用）。此前若有"老机型可用"的说法，与源码不符。

### 唯一消费点：`Output::getHdrSdrRatio`

- A15：[Output.cpp:1756](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/android15-release/services/surfaceflinger/CompositionEngine/src/Output.cpp)；A16 main：Output.cpp:1802。**整个 surfaceflinger 目录只有这一处消费**（rg 全量核实）。
- 逻辑（A15 源码逐行核对）：
  1. flag 关 → 恒返回 `1.0f`；
  2. flag 开 → 还需同时满足：client target buffer 是 `RGBA_FP16`、dataspace 属于 extended range、`displayBrightnessNits/sdrWhitePointNits` 元数据有效，否则**仍返回 1.0**；
  3. 全部满足 → 返回 `displayBrightnessNits / sdrWhitePointNits`。
- 返回值的下游：
  - `composeSurfaces` 中 `targetLuminanceNits = clientTargetBrightness × displayBrightnessNits × (1/ratio)`（GPU 合成时告知 RenderEngine 目标亮度，用于 HDR 场景下 SDR 层的相对亮度正确性）；
  - `queueBuffer(..., getHdrSdrRatio(buffer))` → `advanceFrame(hdrSdrRatio)` 传给 HWC 侧。
- **重要语义修正**：flag 描述写"是否渲染到 FP16 client target"，但在 A15/A16 实现中它**并不改变 client target 的格式分配**（RenderSurface 默认 RGBA_8888；实际格式由 HWC 通过 `clientTargetProperty.pixelFormat` 经 `Display::applyClientTargetRequests` 决定）。该 flag 只是"亮度比值上报"的开关。描述是历史遗留，与实现有出入。
- 覆盖优先级：`getFlagValue`（FlagManager.cpp:58-64）= **sysprop 覆盖值优先于 aconfig 构建值**。即 ROM 官方即使构建时关闭该 flag，`debug.sf.fp16_client_target=true` 也能打开它。
- 读取时机：宏实现为 `static const std::optional<bool> debugOverride = getBoolProperty(...)`——**SF 进程首次访问时读取一次并永久缓存**，运行时 `setprop` 不改变已缓存值 → 改动后必须重启 SurfaceFlinger 进程才生效。

### 副作用面（第 6 搜索方向）

- 内存/带宽：**无影响**。该 flag 不触发任何 buffer 分配、不改变格式（上述语义修正），FP16 化带宽翻倍之类的担心在此 prop 上不成立。
- SDR 内容：仅在 "client target 已是 FP16 且 dataspace extended" 的 HDR GPU 合成场景下，SDR 层亮度会被重新映射（设计目的即如此）。SDR 纯静态场景短路返回 1.0，行为不变。
- 性能：每帧多几次浮点判断与除法，可忽略。

## ③ 风险矩阵

| 场景 | 结果 | 判据 |
|---|---|---|
| Android 13/14 设备 | prop 完全无效（flag 不存在），无任何行为变化 | `getprop ro.build.version.sdk` ≤ 34 |
| Android 15+，client target 非 FP16（绝大多数设备的 SDR 日常场景） | `getHdrSdrRatio` 短路返回 1.0，**行为与关闭时逐比特一致**；无害，多半也无感 | `dumpsys SurfaceFlinger \| grep -i fp16` 显示 true 但画面无变化 |
| Android 15+，client target 为 FP16 且 extended range（HDR 内容触发 GPU 合成、HWC 报告 FP16 client target 的设备，多为较新 HDR 设备） | flag 生效：SDR 层 `targetLuminanceNits` 被除以 HDR/SDR 比值 → SDR 元素变暗（这是上游设计目的：HDR 场景下保留 SDR 相对亮度）。**若 ROM 依赖旧行为或亮度元数据异常，可能出现 HDR 播放时 UI 亮度突变/过暗类视觉异常** | 播放 HDR 视频时观察周围 UI 亮度是否跳变 |
| 崩溃/启动失败 | **源码层面不存在此路径**：flag 只在帧合成路径做浮点计算，不触碰 gralloc 分配、不触碰 HWC 初始化。所谓"不支持的设备开它导致 SF 起不来/黑屏"没有源码依据 | — |
| 回退行为 | 关闭 prop 后重启 SF 即完全回到原行为；flag 只影响一个亮度比值，无持久化副作用 | `dumpsys SurfaceFlinger` 验证 |

- "高通老 HWC（composer3-V2/V3 NDK 时代）设备开此 prop 的已知结果"：**无公开案例**（全网无检索命中）。按源码推导：老 HWC 不上报 FP16 clientTargetProperty → flag 停在短路分支 → 无效但无害。此条为源码推导，无社区实证，如实标注。

## ④ KernelSU system.prop 时序（文档证据）

来源：[KernelSU 官方模块文档](https://kernelsu.org/guide/module.html)（全文抓取核对）：

1. Boot 流程图明确显示：`post-fs-data` 阶段执行 `*(pre)load system.prop (same as resetprop -n)`，随后才是 `class_start core`（启动 logd、vold 等）与 `class_start main`（zygote 等）。
2. [surfaceflinger.rc（A15 源码）](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/android15-release/services/surfaceflinger/surfaceflinger.rc)：`service surfaceflinger /system/bin/surfaceflinger` 属于 `class core animation`。
3. 结论：**KSU/Magisk 模块的 system.prop 中写入 `debug.sf.fp16_client_target=true`，其设置时点严格早于 SurfaceFlinger（class core 服务）启动**，SF 首次读取 flag 时一定能拿到值。时序上 system.prop 方案成立。
4. 附带证据：同文档警告 post-fs-data 阶段直接 `setprop` 会死锁 boot，必须用 `resetprop -n`——system.prop 机制内部正是以 `resetprop -n` 实现，所以用 system.prop 文件而非脚本 setprop 是正确姿势。
5. Magisk 侧：KSU 文档自述 "The module mechanism of KernelSU is almost the same as that of Magisk"；Magisk 的 system.prop 机制相同，但本次未单独抓取 Magisk 官方文档核对时序，如实标注。

## ⑤ 最终建议

**能否放心让用户装模块（system.prop 写入此 prop）？——技术上"放心"，效果上"大概率无效"，上线前必须软重启实测。**

1. **安全性**：可以放心。源码层面无崩溃/bootloop 路径（flag 只 gate 一个亮度比值计算）；A13/A14 完全无效；A15+ 在 client target 非 FP16 时行为逐比特不变。最坏情况是 "HDR GPU 合成时 SDR UI 亮度被重映射" 的视觉异常，关闭并重启 SF 即可完全回退。
2. **有效性存疑**：唯一实证分发来源是 Telegram tweak 圈（SOSP/haruhi kernel，DWYOR 性质，无任何结果反馈；mtkVEST 仅索引级证据）。该 prop 对联想平板这类设备是否生效，取决于其 HWC 是否上报 FP16 client target——不验证就分发属于盲改。
3. **与本项目目标的关系**：此 prop 只影响 SurfaceFlinger 合成阶段的亮度上报，**与 Ultra HDR 图片的应用内 gainmap 渲染没有直接因果关系**，不应指望它修复 Ultra HDR 问题。
4. **实操路径**（推荐固化前流程）：
   - 先 `setprop debug.sf.fp16_client_target true && killall surfaceflinger`（软重启 SF，无需整机重启）；
   - `dumpsys SurfaceFlinger | grep -i fp16` 确认值为 true；
   - 播放 HDR 视频观察 UI 亮度是否异常、Ultra HDR 目标场景是否确有改善；
   - 无异常且有效，再写入模块 system.prop；无效则移除（避免与未来其他 tweak 互相污染排查）。
