## ① 致命问题：日志为什么不写（完整链路判定树）

按可能性从高到低，四层原因叠加。每一层都有代码级证据。

### A. 用户看的"文件"是 sdcard 路径，而该路径在这台设备上从未生成过（最可能）

- 模块 v2.0.5 的 FileLog 写入顺序是 **`/data/system/hdrfix.log` 第一优先、sdcard 仅是镜像**（HdrRatioFix.java:826-832 注释与 `PATHS` 数组）。
- sdcard 目录由 KSU 的 service.sh 在开机早期创建：`ksu-module/service.sh:15-21`，`mkdir -p "$SDIR" 2>/dev/null`。**开机 late_start 阶段 FUSE/sdcardfs 视图常常还没挂载，mkdir 失败且错误被 `2>/dev/null` 吞掉**，后续 seed、chmod 全部静默失败。
- 项目自己的提交记录已经承认这一点——v2.0.2 提交（d300fb6）原文："sdcard路径依赖KSU模块service.sh建目录，**用户设备从未建成** → 日志一直只在/data/system/hdrfix.log"。
- 结论：文件管理器里 `/storage/emulated/0/hdr日志/hdrfix.log` **永远不会出现**，与点不点"清除"无关。用户"连文件都没有生成过"的直观观察首先来自这里。而 `/data/system/hdrfix.log` 需要带 root 的文件管理器才能看到，用户看不到 ≠ 不存在。

### B. 历史链（9.2 / v1.1.x 时代"能写"→ 之后"不写"的直接机制）

git 比对给出决定性证据：

1. **v1.1.x 模块的 `log()` 无条件写文件**——`git show fbdf547`（v1.1.8）中 `log()` 只有 `XposedBridge.log + FileLog.write` 两行，**根本不读 PROP_LOG**。这就是"v1.1.x 日志能写"的真正原因（不是日志开关开没开）。
2. **v1.1.x 时代 App 的清除按钮是 `rm -f`**（旧 Shell.kt clearLog：`su("rm","-f",path)`）。unlink 之后，v1.1.x 模块的 BufferedWriter 持有的是孤儿 inode 句柄：`write()` 不抛异常、`anyWritten=true`、连 "ALL PATHS failed" 诊断都不触发（HdrRatioFix.java:868-902 的失败检测全部依赖抛异常）。**文件从此在目录里消失，直到重启 system_server**。
3. "点了清除按钮之后，根本连文件都没有生成过"与 **v1.1.x App rm + v1.1.x 模块无自愈** 这对组合 100% 吻合。v2.0.1（模块 2 秒 stat 自愈，HdrRatioFix.java:854-867）+ v2.0.2（App 改 toybox truncate，Shell.kt:40-50）已经修复了这对组合，但用户的观察来自修复前的体验。

### C. v2.0.0~v2.0.4 的 PROP_LOG 永久关闭陷阱（App 侧嫌疑的实锤）

- v2.0.0 起，模块 `log()` 新增开关检查：`if (!SysProps.getBoolean(PROP_LOG, true)) return;`（HdrRatioFix.java:752-753）。`persist.*` prop **一旦被写成 "0" 就永久保留**。
- **App 有两条路径会永久写入 LOG="0"**：
  - "详细日志"开关本身：ControlsPage.kt:103-106（`apply(Props.LOG, if (it) "1" else "0")`）；
  - **"恢复全部默认"按钮：ControlsPage.kt:171（`Shell.setProp(Props.LOG, "0")`）**——用户以为在重置，实际把日志永久关死。
- v2.0.5 之前模块**没有 logAlways 绕过**（v2.0.5 提交 6728e77 才加入）。若用户在 v2.0.0~v2.0.4 期间关过"详细日志"或点过"恢复默认"，模块几乎不写任何文件 → `/data/system/hdrfix.log` 停止增长 → "文件没有生成/没有内容"。
- v2.0.5 的 logAlways（HdrRatioFix.java:747-750）绕过了该开关，**但前提是 LSPosed 里模块真的重载到 v2.0.5 且 system_server 已重启**。

### D. 现状（v2.0.5 组合）剩余的失败模式

- 只装了新 APK、没有在 LSPosed 重启系统界面/手机 → system_server 里跑的仍是旧代码（模块 dex 打在 APK 里，LSPosed 不热重载 system_server 模块）。
- 模块未激活 / LSPosed 作用域丢失 / `disable=1`（disable 只在模块加载时读一次，见 ②-1）。

### App 侧日志链自身的真实 bug（即使在 v2.0.5 也存在）

| # | 位置 | 问题 |
|---|---|---|
| A1 | Shell.kt:48-49 | `clearLog` 在 truncate 失败时**回退 `rm -f`**——重演孤儿 inode 陷阱。v2.0.1+ 模块自愈兜底，但自愈由 `write()` 事件驱动（含 5 分钟心跳，HdrRatioFix.java:845-849），最坏 5 分钟文件缺失；若模块未激活则永久缺失。回退路径完全违背了 41-47 行注释自己阐述的原理 |
| A2 | Shell.kt:64,69-72; LogsPage.kt:44-48,111-115 | **App 的读取优先级（sdcard 优先）与模块写入优先级（/data/system 优先）相反**。在 service.sh "半成功"（目录建出但 system_server 写 FUSE 被拒）的设备上：`readLog()` 会读到只有一行 "boot seed" 的 sdcard 文件（非空即返回，Shell.kt:69-72），真实日志被遮蔽；导出按钮（LogsPage.kt:111-115）同样导出残缺文件 |
| A3 | strings.xml:35（en/zh 同） | "日志落盘"文案写"镜像日志到 **/data/local/tmp/hdrfix.log**"——v1.0.4 之前的古董路径，现为 /data/system/hdrfix.log + sdcard 镜像，且该开关本身已死（见 ②-4） |
| A4 | Shell.kt:67 + ControlsPage.kt:55 vs HdrRatioFix.java:753 | **log 开关的 UI 初始态与模块默认值相反**：prop 未设置时 `Props.bool()` 判空 → UI 显示"关"；模块 `getBoolean(PROP_LOG, true)` 默认却是"开"。用户看到开关是关的，误以为日志被关（实际在写）；或反过来去"打开"它才真正写 "1" |
| A5 | Shell.kt:12-19 | `su()` 只读 stdout，**stderr 从不消费且无超时**：`su 0 dumpsys display` 若 stderr 管道（64KB）被写满，进程阻塞 → `waitFor()` 永久挂起 → Dispatchers.IO 线程泄漏。dumpsys 正常时 stderr 极小，属低概率但真实的死锁面 |

**"日志不写"最可能结论**：sdcard 文件本来就不会生成（A 层）+ 历史上 v1.1.x 的 rm 清除造成过永久断写（B 层）+ v2.0.0~2.0.4 期间 PROP_LOG 可能被"恢复默认"永久关死（C 层）。三层叠加，用户看到的现象完全成立；v2.0.5 组合（logAlways + 自愈 + truncate）在**模块真正重载**后应已闭环。

## ③ 其他发现

1. **App 版本与模块版本双硬编码**：App `versionName "2.0.5"`/versionCode 26（app/build.gradle.kts defaultConfig）与模块 `VERSION = "2.0.5"`（HdrRatioFix.java:76）当前同步，但无单一来源，历史上有失步空间。AboutPage 显示 App 版本（BuildConfig，AboutPage.kt:97），StatusPage 显示模块版本（prop/SP，StatusPage.kt:49-50）——两处不一致恰恰是"APK 已更新但模块未重载"的现成检测信号，目前没有利用。
2. **HdrTestActivity 亮度扫描的 4 处 bug**：
   - HdrTestActivity.kt:283 恢复亮度时不校验 `savedBr`：读取失败时其值为 `"?"`（:230-232 的 `ifEmpty { "?" }`），`settings put system screen_brightness "?"` 会写入非法值；
   - HdrTestActivity.kt:302-304 异常兜底把 `screen_brightness_mode` 硬编码恢复为 `"1"`（自动亮度），而非保存的 `savedMode`，且不恢复亮度值——中途失败则亮度停在出错档位；
   - HdrTestActivity.kt:293-297：`tmp.writeText(sb)` 在 append "saved -> …" 行**之前**执行，导出的 hdrscan.log 永远缺最后一行（仅 App 内显示有）；
   - 所有 `settings put` 返回值不检查（:236,241,283,286），root 失败静默继续，扫描结果整体失真。
3. LogsPage.kt:44-48 "实际生效路径"的判定依据是**文件是否存在**（`ls`），不是"模块在写哪个"：文件不存在时显示 fallback 路径，可能让用户误以为模块正写到 /data/system（实际可能根本没在写）。
4. 检查更新指向 `wxz2672554287/Lenovo-Tab-UltraHDR-Fix`（AboutPage.kt:30,54）与 git remote 一致；国内直连 api.github.com 大概率 `update_failed`（无代理机制），属体验问题非 bug。
5. 首启时序安全：EULA → 主界面 → 各页 LaunchedEffect 才发起 su；无 root 时 `su()` 返回 null，界面显示"未知/未激活"，**不会崩溃或空白**。Manifest 中 HdrTestActivity 已注册，xposed_scope 含 `android` + 自身（arrays.xml），自钩子（App.onCreate 写 hook_status）的作用域声明齐全。
6. ControlsPage.kt:51-59 在 `Dispatchers.IO` 协程内直接写 `mutableStateOf`（Compose 快照系统允许，但属反模式）；LogsPage.kt:44-50 的 `logPath` 与 `content` 分两段异步更新，切换瞬间可能出现"新路径 + 旧内容"的短暂错配。
7. Shell.su 每个属性一次 `su 0` 进程（fork+授权开销数百 ms）：开关页加载串行 6 次 su、恢复默认连发 5 次（ControlsPage.kt:169-173），低端机上页面状态"慢半拍"。
