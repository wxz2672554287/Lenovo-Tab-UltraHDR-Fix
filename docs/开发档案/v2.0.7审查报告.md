## 重点审查清单逐项结论

### 1. 重入/递归安全 —— 结论:同线程收敛成立;跨线程竞态下无护栏【重要→见 B4】

- **同线程重入必然收敛**:F 写口(HdrRatioFix.java:342)`floatDiffers(fieldVal, target)` 中,`fullBootstrap`(:582)在 `synchronized(syncRoot)` 内写 `mCurrentHdrSdrRatio=target`(:593)后调用 `updateDeviceInfoLocked()` → 同步重建 `mInfo` → `getDisplayDeviceInfoLocked` 再入 hook。此时 `fieldVal == target`(同一线程已写,且经 syncRoot 监视器有 happens-before);重入时 `bootstrapRatio()` 的输入(obs 缓存/字段)在本线程内未变 → `target' == target` → `floatDiffers=false` → 只走 heal 分支(:354)→ 不再 fullBootstrap。**稳态收敛、无无限递归的主路径成立**。
- **但收敛依赖"obs 未变"这一未被保证的前提**:`sObservedSdrNits/sObservedMainNits` 由 setDisplayBrightness(nitsCapture,:382-408)在 DPC 线程写入,与 DMS 线程的 F 写口并发。若嵌套 fullBootstrap 执行期间 obs 被并发更新且 ratio 变化 ≥0.005,重入会再次 `floatDiffers=true` → 再次 fullBootstrap → 嵌套加深。代码**没有任何重入计数/深度护栏**,理论上存在链式嵌套(实测概率极低:要求毫秒级窗口内 obs 连续跳变,几何衰减,栈深远达不到溢出阈值,但属"靠物理参数巧合保证安全"而非结构保证)。v2.0.1 的让位分支是结构性终止,v2.0.7 把终止条件从"结构"换成了"数值收敛",丢了护栏。
- **附带竞态**:`floatDiffers` 判定在锁外(:342),两个 binder/handler 线程可同时判 true → 双写 + 双 `updateDeviceInfoLocked` + 双事件(值相同则幂等,仅浪费);若两线程算得不同 target(T1 旧、T2 新),`fullBootstrap` 锁内**不复查**直接写(:593),可能出现旧值后写覆盖新值(瞬态,下次读取自愈)。
- **修法**:`fullBootstrap` 的 `synchronized(syncRoot)` 内先重读字段并复查 `floatDiffers(field, target)`,不同才写;可选再加一个 `AtomicBoolean sBootstrapInFlight` 去重。一处修改同时解决递归护栏、双事件、旧值覆盖三件事。

### 2. 死锁 —— 结论:无死锁 ✓

- `getDisplayDeviceInfoLocked` 的所有调用方均持 adapter syncRoot(DMS 全局锁);`fullBootstrap` 里 `synchronized(syncRoot)`(:609)为**可重入**获取,不会自锁。`getSyncRoot()` 反射失败时降级为无锁 `body.run()`(:612),而当前线程本就持锁,仍安全。
- `updateDeviceInfoLocked` 的行为:**mInfo 重建是同步的**(即触发 hook 重入的路径),**事件分发是异步的**(经 handler post,无同步回调进 DMS),不构成锁环。
- `FileLog.write` 的类锁是叶级锁(内部不再获取其他锁),与 syncRoot 无环。
- 唯一注意点(非性能外无碍):**全部 hook 逻辑含文件 I/O(FileLog write+flush)都在 syncRoot 内执行**——DMS 是 system_server 最热锁之一,见【建议 S7】。

### 3. 并发 —— 结论:可接受的良性疾病 + 一处真实缺口(归入 B4)

- `nitsCapture` 连写 3 个 volatile(:397-399)非原子:读取侧可能拿到"新时间戳+旧 nits"或 main/sdr 撕裂对。因 nits 物理连续、且 bootstrapRatio 优先只读 `sObservedSdrNits`,实际影响可忽略;若要求严格,可将两通道+时间戳封装为一个不可变 volatile 对象。
- 多线程 F 写口并发:见清单 1 附带竞态(双事件幂等、旧值覆盖自愈)——真实缺口由 B4 修法覆盖。
- `sLastMode`/`sLastLogObsMs` 等节流变量的并发:最坏重复打一条日志,无害。

### 4. 事件风暴 —— 结论:与 A15 原生同量级,可接受 ✓【建议 S8 可选优化】

- 写入(即事件)的双重闸门:`floatDiffers(field, target)` 且 target 只随 obs 变化而变 → **事件率 ≤ setDisplayBrightness 参数变化率**。亮度拖动时约每帧一次(≤60/s),亮度静止时零事件(:286 注释声称"亮度静止时零开销",核实属实:字段≈target 时既不写也不发事件,heal 分支也因 `existing` 恒等于字段拷贝而不触发)。
- A15 原生 handle 对 ratio 用精确浮点比较,动画期间同为每帧级事件;0.005 阈值比原生**更粗**,不构成比原生更大的风暴。App 侧 EVENT_DEVICE_INFO_ADJUSTED→DISPLAY_CHANGED 的 60/s 重算与原生亮度动画的既有负载同型。
- 数值核对:30%→100% 拖动 ratio 全程变化约 0.77(1.77→1.0),每帧 Δ≈0.026>0.005,确实是"每帧都写";若想减负可提到 0.01(视觉无差),但非必需。

### 5. 边界 —— 结论:健康 ✓

- `target == 1.0`:外层判 `target >= 1.0f`(:341)通过,`floatDiffers(NaN, 1.0)=true` → 诚实写入 1.0 + 事件。这是 v2.0.7 有意的"100% 亮度无 headroom 也如实上报",与 DPC 的 800nits 钳制逐点一致。副作用:1.0 时 ViewRootImpl 会把 HDR 窗口降级为宽色域——但物理上此时确无抬亮空间,语义正确。
- `sLastGoodRatio = target > 1.0f ? target : sLastGoodRatio`(:344):target=1.0 时不污染兜底值;`lastGoodRatio()`(:567)又要求 `>1.0f` 否则回 1.5,双保险,**无 NaN/0 值进入兜底链**。
- `bootstrapRatio` 是否可能返回 NaN:**不可能**。nits 无效时走 `lastGoodRatio()`(恒 1.5 或已验证的有效值);各分支 `nitsValid` 前置过滤 NaN/Inf/≤0。F 写口的 `!Float.isNaN(target)` 判断(:341)是冗余但无害的保险。
- `interp()` 对 x<4(返回 4.0)与 x>502(返回 1.593)、800/sdr 钳制、userMax 钳制、下限 1.0 钳制的叠加次序(:549-558)核对无误。

### 6. mode 切换时序 —— 结论:mode 维度无残留 bug ✓

- mode 0/1 → 2:`legacyWrite`(:629)每次直写 info+字段,覆盖连续写入者的值,行为即 v1.1.8 对照,无残留问题。
- mode 2 → 0/1:字段=legacy 主通道失真值 → mode0 首读 `floatDiffers=true` → 立即重写为 SDR 通道值 + 事件,自愈。
- mode 1 ↔ 0:apply hook(:253)与 F 写口均每次回调动态读 mode,切换干净。
- `legacyWrite` 中 `sLastGoodRatio = targetRatio`(:669)无条件赋值,可能在 100% 时存入 1.0,但 `lastGoodRatio()` 的 `>1.0f` 校验(:568)兜住 → 切回 mode0 后兜底仍为 1.5,正确。
- 唯一的"切换残留"问题在 **disable**(见清单 7/B2),不属于 mode。

### 7. PROP_DISABLE 动态检查位置 —— 结论:检查位置本身合理,但 disable 语义有三个实缺口【重要 B2】

检查位于 `existing` 读取之后、一切写入之前(:317-319),"不产生新写入"的目标达成。但:
1. **字段值永久残留**:v2.0.7 定案"模块是 mCurrentHdrSdrRatio 唯一活写入者",disable 后再无任何写入者 → 字段冻结在最后一次写入值(如 1.5),系统每次 `getDisplayDeviceInfoLocked` 重建都会把它拷进 info,**App 永远读到旧值**。而 App 的停用确认弹窗文案(`values-zh-rCN/strings.xml:100`)明确承诺"**回到出厂的 NaN 行为**"——文案与实现直接矛盾,这是 v2.0.7"持续写入者"定性后新产生的行为缺口(v2.0.6 时代理论上还有系统 handle 兜底,现在没有了)。
2. **disable 不约束 HOOK 1/2/3**:`handleHdrSdrNitsChanged` 的 mode2 短路(:157)、`hasSdrToHdrRatioSpline` 的 mode2 强制 false(:201)、`HdrBrightnessModifier.apply` 的 mode1 抑制(:253)都只看 mode、不看 disable → "停用模块(总闸)"开启后 mode1 的面板抑制、mode2 的短路照常生效,总闸名不副实。
3. 次要:hookObb 的 FIELD FAIL 日志(:310)在 disable 检查**之前**且无节流,若未来 OTA 字段改名,即使停用也刷 FAIL 洪水。
- **修法**:在 F 写口内检测 disable 上升沿(记一个 `sLastDisable`),翻转时执行一次"卸载写"——字段写 NaN(出厂态)+ `updateDeviceInfoLocked()` 发事件,真正回到出厂 NaN 行为;HOOK 1/2/3 的 before 中加同样的 disable 早退;FAIL 日志加节流或挪到 disable 检查之后。

### 8. handle 观察 hook 的 this$1 链路 —— 结论:正确 ✓

`listenerClass = LocalDisplayAdapter$LocalDisplayDevice$1`(:137),按 javac 合成字段命名规则,二级嵌套类的立即外围引用名为 `this$1`(类型 = LocalDisplayDevice),`this$0`(类型 = LocalDisplayAdapter)则在 LocalDisplayDevice 上。所以:
- HOOK 1 after 里 `getObjectField(param.thisObject, "this$1")` → LocalDisplayDevice → 读 `mCurrentHdrSdrRatio`(:173-176)✓;
- HOOK 4/`bootstrapRatio`/`legacyWrite` 在 device(thisObject 即 LocalDisplayDevice)上取 `this$0` → adapter(:502, :632)✓;
- nitsCapture 直接在 thisObject($1)上调 `brightnessToBacklight/backlightToNits`,与 v2.0.5 的 smali 核实及实测(nitsCapture main=755 sdr=542)一致 ✓。
- 附注:由于运行时 hasSpline=false、handle 永不被调,这段 after 代码实际休眠;若字段名有误也只能等 handle 复活才暴露,且异常被 `catch (Throwable ignored)`(:183)静默——链路静态判定正确,但建议把 ignored 至少改为低频诊断日志。

### 9. logAlways 在 FileLog 全 EACCES 设备上的行为 —— 结论:无递归循环 ✓,但噪音放大【建议 S6】

- 失败路径:每条 logAlways/log → `FileLog.write` 尝试两个路径 open 失败 → 各打一行 `FileLog FAIL`(只进 XposedBridge.log,**不回写 FileLog,无自我递归**);`diagFailedOnce()`(:919)保证 "ALL PATHS failed" 只打一次。
- 实际代价:每条日志膨胀为 3 行 logcat,且每次都做 2 次注定失败的 open()(发生在 DMS 锁内);`captureModuleLogcat` 的抓取结果会被成对的 FAIL 行污染(节流日志尚可,拖动期间 RATIO 行每帧一条 → FAIL 行 120/s)。
- **修法**:连续 N 次(如 3 次)open 失败后进入熔断,退避(如 60s)后重试一次,期间 `write()` 直接短路。

### 10. App 侧新函数与字符串 —— 结论:4 项问题(见 B3/B5/B6/S3)

- **HdrTestActivity 亮度扫描**:v2.0.7 未触碰(不在两个 diff 的文件清单中),其引用的 `Shell.su/cp` 签名未变,不受影响 ✓。
- **Shell.su 本体**(:12-19):只读 stdout、不消费 stderr(`logcat -d` 正常路径 stderr 极少,仅理论上 >64KB stderr 可使子进程阻塞 → `readText` 永不 EOF)、`waitFor()` 无超时(su 卡在授权弹窗时 IO 协程线程被无限占用)。v2.0.7 最大的调用(`logcat -d` 全量)放大了这两个旧毛病,见 B6。
- **captureModuleLogcat**(:90-95):过滤逻辑正确(XposedBridge.log 输出必带 `[HDRRatioFix]`,按内容过滤不依赖 tag;`su 0 logcat -d` 参数逐个传递,无 `-c` 拆词问题);但全量 dump(数 MB 级)→ 过滤串 → 一次性塞进单个 Compose `Text`(LogsPage.kt:197-204),大文本单 Text 渲染有卡顿/ANR 风险,见 B6。
- **repairLogFile**(:62-67):三步 touch/chown/chmod 均为 root 单命令(无引号转义问题)✓;但**返回值 = chmod 的退出码**,root 下 chmod 几乎恒成功 → 即使 SELinux context 不对(system_server 依然 EACCES)也返回 true,自愈失败用户无感知;且未做 `restorecon`。历史上"KSU 脚本预创建后可写"实证了该机制大体可行,但新文件 context 是否与当年一致未经验证,见 B5。
- **repairSdcardLog**(:74-80):尽力而为、失败静默,符合注释;chmod 777 目录略宽(small security nit,FUSE 上 chmod 也可能被忽略);触发的空文件会引出 B3 的两个问题。
- **LogsPage refresh 自愈**(:49-63):逻辑、线程(withContext(IO) 内改 mutableStateOf 合法)、Toast 主线程回调均正确;修复失败 Toast 仅在 chmod 失败时出现(受 B5 影响,几乎不会触发)。**但它创建的 sdcard 空文件让既有的"路径显示/导出"选择逻辑走向错误分支,见 B3**。
- **字符串**:4 组新字符串在 `values/` 与 `values-zh-rCN/` 均已定义,引用处 `R.string.log_capture_logcat/log_capture_empty/log_repair_fail/log_logcat_section` 一一对应 ✓;仓库仅这两个 locale 目录,无漏翻 ✓;Kotlin 侧 import(Toast/FontFamily)齐备,可编译 ✓。
