- 日期:2026-09-05

- 调查方式:AOSP 源码/文档(TinyFish + Exa 双渠道)+ 366 官方固件 surfaceflinger 二进制本地反汇编(capstone aarch64)
- 本地证据文件:`D:\桌面\pro gt搞机\救砖镜像\解包分析\hdr\extracted\system_a__366__surfaceflinger`(7,990,752 字节)

## 0. 一句话结论(推翻前一轮定案)

**KSU 不但撬得动,而且根本不用 patch 二进制:`debug.sf.fp16_client_target` 这个 debug prop 是 SurfaceFlinger 自带的、无条件优先于 aconfig flag 的运行时覆盖通道,对 fixed_read_only flag 同样生效。一个 SukiSU 模块 + 一行 `system.prop` 即可打开 FP16 client target。**

> ⚠️ 前一轮"该 flag 无 debug prop / device_config 可控项"的结论**是错的**。SurfaceFlinger 的 FlagManager 机制给它的每一个 aconfig flag 都配了 `debug.sf.*` prop 覆盖宏(见 §2 证据 1/2)。device_config 不可控是对的,但 prop 通道一直都在。

## 1. 结论矩阵(路径 × 可行性 × 代价 × 风险)

| 路径 | 可行性 | 代价 | 风险 | 备注 |
|---|---|---|---|---|
| **d. `debug.sf.fp16_client_target=true` prop(KSU system.prop)** | ✅ **完全可行,强烈推荐** | 极低(一个文本模块) | 低:需重启 SF/整机生效;HWC/GPU 对 FP16 client target 的兼容性待实机验证;FP16 合成增加 GPU 带宽 | 唯一被编译进 366 二进制的活开关 |
| c. patch surfaceflinger 二进制(改 flag 判定恒真) | ⚠️ 可行但**完全不必要** | 中(定位指令、替换、magic mount) | OTA 覆盖后需重做;体积/校验风险 | prop 后门存在时纯属绕远路 |
| a. systemless overlay `/system/etc/aconfig/*.pb` | ❌ 无效 | - | 白折腾 | flag 值不在 build 时 pb 里被 366 读取;编译器已把该 flag 折叠成常量 false(§2 证据 3) |
| b. 直改 `/metadata/aconfig` 存储(RW flag val/info) | ❌ 无效 | - | 损坏 aconfig 存储风险 | `fp16_client_target` 是 `is_fixed_read_only:true`;aflags/aconfigd 只允许覆盖 READ_WRITE flag;且 366 的 SF 根本不在运行时读 storage |
| e. HWC 侧(改上报让 SF 选 FP16) | ❌ 路线错 | 高(patch vendor) | 高 | client target 格式由 **SF 侧 flag** 决定,不是 HWC 能力上报(§2 证据 4);patch vendor 更难且无关本问题 |
| adb shell `cmd device_config` / `aflags enable` | ❌ 无效 | - | - | 只对 READ_WRITE flag 有效;366 为 user build,fixed_read_only 直接拒绝 |

**推荐路径:路径 d。** 若未来固件(>366)移除了该 prop 通道,再考虑路径 c(方法论见 §5)。

## 2. 决定性证据链

### 证据 1:AOSP 源码 —— FlagManager 为每个 flag 配了 prop 覆盖通道

`frameworks/native/services/surfaceflinger/common/FlagManager.cpp`(AOSP main,对应 Android 16):

```cpp
bool getFlagValue(std::function<bool()> getter, std::optional<bool> overrideValue) {
    if (overrideValue.has_value()) {
        return *overrideValue;      // ← prop 有值则无条件生效,没有任何 build type 检查
    }
    return getter();                // aconfig flag 值兜底
}

#define FLAG_MANAGER_CONFIG_INTERNAL(name, syspropOverride, owner)          \
    bool FlagManager::name() const {                                        \
        static const std::optional<bool> debugOverride = GetBoolProperty(syspropOverride); \
        static const bool value = getFlagValue([] { return owner::name(); }, debugOverride); \
        if (mUnitTestMode) { return owner::name(); }                        \
        return value;                                                       \
    }
#define FLAG_MANAGER_CONFIG_FLAG(name, syspropOverride) \
    FLAG_MANAGER_CONFIG_INTERNAL(name, syspropOverride, flags)
...
FLAG_MANAGER_CONFIG_FLAG(fp16_client_target, "debug.sf.fp16_client_target")
```

要点:
- `debugOverride` 是 **static 一次初始化** → prop 在 SF 进程内只读一次(首次调用该函数时),之后永久缓存 → **中途 setprop 不生效,必须在 SF 启动前设置,改完必须重启 SF 或整机**;
- 覆盖逻辑对 `is_fixed_read_only` 的 flag 同样有效(fixed_read_only 只挡 aconfig 的 override 体系,不挡 FlagManager 的 prop 通道);
- `GetBoolProperty` 是虚函数,真实实现即 `base::GetBoolProperty(prop, "")`。

### 证据 2:AOSP flag 声明 —— 确认 fixed_read_only + prop 名

`services/surfaceflinger/surfaceflinger_flags.aconfig`(AOSP main,base64 原文解码):

```
flag {
  name: "fp16_client_target"
  namespace: "core_graphics"
  description: "Controls whether we render to fp16 client targets"
  bug: "236745178"
  is_fixed_read_only: true
}
```

- 确认 `is_fixed_read_only: true` → aflags / device_config / aconfigd override 全部不可用(`aflags` 源码显式 `ensure!(flag.permission == ReadWrite, "read-only for the current release configuration")`;DeviceConfigService 对 aconfig RO flag 报 "cannot write read-only flag")。
- fixed_read_only 只意味着 aconfig 体系内不可变,**不拦截 FlagManager 的 prop 覆盖**(证据 1 的宏优先级在 aconfig 读取之前)。

### 证据 3:366 二进制反汇编 —— prop 是唯一活开关,aconfig 已被编译期折叠

字符串证据(strings):
- `0x51684`:`debug.sf.fp16_client_target`(FlagManager prop 名)
- `0x57e16`:`fp16_client_target`(dumpsys 输出用 flag 名)
- `0x69e44`:`RGBA_FP16`(格式名字符串)
- 动态链接 `libaconfig_storage_read_api_cc.so`(aconfig 框架在,但见下文,fp16 这条不走 storage)

xref 与反汇编(capstone aarch64):

**(a) FlagManager::fp16_client_target() = 0x700904**(由 dumpsys dump 函数 0x6fd0b0 处的函数指针 + 格式串调用链确认):

```
0x70097c-0x7009cc  guard A 初始化体:
    bl 0x705f60            ; __cxa_guard_acquire(static debugOverride)
    adrp x1, 0x51000 ; add x1, x1, #0x684   ; x1 = "debug.sf.fp16_client_target"
    ldr x8,[x0]; ldr x8,[x8,#0x10]; blr x8   ; 虚调用 GetBoolProperty(prop)
    strh w0, [0x7502e8]    ; 结果(std::optional<bool>)入全局缓存

0x7009d0-0x700a30  guard B 初始化体(value):
    ldrh w8, [0x7502e8]    ; 读 debugOverride {value, engaged}
    and  w11, w8, #0x100   ; engaged?
    and  w8, w8, w11, lsr #8
    strb w8, [0x7502f8]    ; value = engaged ? prop值 : 0
```

**关键观察:guard B 体内没有任何 aconfig storage 读取调用**(整个函数只 BL 了 `__cxa_guard_acquire(0x705f60)` / `__cxa_guard_release(0x705f90)` / 栈检查失败处理器)。`getFlagValue` 的 getter(lambda → aconfig 读函数)被编译器完全优化掉了 —— **release build 中 fixed_read_only+false 的 aconfig flag 被预折叠为常量 false**,整个表达式化简为 `value = engaged ? prop : false`。

→ **366 上该 flag 的值唯一可变通道就是 `debug.sf.fp16_client_target` prop。** 这也意味着路径 a/b(aconfig pb / metadata 存储)在 366 上物理无效:二进制根本不读它们。

**(b) 业务消费点 1 = 0x2fce6c(HDR 亮度比 / displayRatio 计算)**:

```
0x2fce94: bl  0x6fbde8            ; FlagManager::getInstance()
0x2fce98: bl  0x700904            ; FlagManager::fp16_client_target()
0x2fce9c: tbz w0, #0, 0x2fcf7c    ; flag==false → 直接 return 1.0 ← 过曝根因!
...
0x2fcef0-0x2fcf04: 取缓冲区像素格式 → cmp w0, #0x16   ; 0x16 = 22 = RGBA_FP16
0x2fcf08-0x2fcf34: 读亮度[0x510]/[0x514]、HDR metadata 字节(掩码 0x38000000==0x18000000)
0x2fcf78: fdiv s8, s8, s0         ; 全部通过 → 返回 亮度比(displayRatio)
```

与任务背景完全吻合:flag 为 false 时该函数恒返 1.0,displayRatio 不参与 HDR 编码 → 高光钳白;打开 flag 且 client target 为 RGBA_FP16 后比率才生效。

**(c) 业务消费点 2 = 0x329020 附近(SDR 白点计算)**:`w21==1` 分支同样询问该 flag,决定是否给白点乘系数。

**(d) dumpsys 输出**:0x6fd0c0 起为 dump 序列("FlagManager values:" 字符串已在二进制中),直接调用 0x700904 并按真假打印 `fp16_client_target: true/false` —— 现成的实机验证手段。

### 证据 4:client target 格式由 SF 侧 flag 决定,HWC 上报不改变它

- 消费点 1 的逻辑是:flag=true 且 SF 分配的 client target buffer 格式==RGBA_FP16 → 比率参与。SF 是格式决策方;HWC 只被动接受 `setClientTarget` 传入的 buffer(AOSP HWC3 API 无"client target 格式协商")。
- 因此"改 HWC 上报"对打开 fp16 无意义(patch vendor 的高代价换不来目标),排除路径 e。

### 证据 5:权限与时序均无障碍

- **SELinux**:SF 读 `debug.sf.*` 属 `debug_prop` 上下文(`system_public_prop(debug_prop)`),SF 大量既有功能(phase offset 等)依赖读 debug.sf.*;本机铁证:**366 官方 build.prop 自己就写着 `debug.sf.latch_unsignaled=1`、`debug.sf.enable_hwc_vds=0`** —— 厂商在用同一通道。root(su 域)设置 debug prop 无限制。
- **331 固件对照**:331 的 surfaceflinger 二进制同样包含 `debug.sf.fp16_client_target` 字符串 → 同机制,新旧固件通吃。
- **社区实践**:Telegram SOSP(Shell Open Source Project)与 mtkVEST G99 频道长期分发含 `setprop debug.sf.fp16_client_target true` 的调优脚本/模块(跨 MTK/Qualcomm 机型),证明该通道在真实用户机上按预期工作。
- **KSU 模块机制**:KernelSU/SukiSU 官方模块规范支持 `system.prop`(由 ksud 在 post-fs-data 阶段用 resetprop 设置,早于 `class core` 的 surfaceflinger 启动),时序上保证 SF 首次读取前 prop 已就位。

### aconfig 存储与修改面(调查问题 1 的正面回答,虽已无必要但补全)

- flag 值存储:`/metadata/aconfig/<container>/` 下的二进制文件(package map / flag map / flag val / flag info),由 aconfigd 在启动时从 build 产物复制生成;读取走 `aconfig_storage_read_api` 的 mmap API(`STORAGE_LOCATION = "/metadata/aconfig"`)。
- `flag info` 每个条目有 `HasServerOverride / IsReadWrite / HasLocalOverride` 位;**RO flag 的 override 位被读端忽略**;`aflags enable/disable`、`adb shell device_config put/override` 均显式拒绝 RO flag。366 的 user build release config 下 surfaceflinger_flags 全部 fixed_read_only。
- 社区没有任何成功修改 aconfig RO flag 值的公开案例(搜遍 aconfigd override / magisk aconfig / aconfig modify 等,唯一相关都是官方 RW flag 流程)。

## 3. 推荐落地方案(SukiSU 模块)

### 第一步:实机快速验证(先确认收益与兼容性,再做成模块)

```bash
adb shell
su
getprop debug.sf.fp16_client_target            # 预期:空(未设置)
setprop debug.sf.fp16_client_target true
reboot                                          # 或:killall surfaceflinger(黑屏数秒,init 自动拉起)
```

重启后验证 flag 已翻转:

```bash
su -c 'dumpsys SurfaceFlinger' | grep -i fp16
# 预期输出:fp16_client_target: true
```

再看效果与异常:
- HDR 片源下高光是否不再钳白、渐变是否恢复(SysTrace/`dumpsys SurfaceFlinger --latency` 辅助);
- GPU 合成帧率/功耗有无异常(`dumpsys gfxinfo`、发热);
- logcat 有无 RenderEngine/HWC 因 RGBA_FP16 client target 报错(gralloc 不支持会分配失败,HWC 不接受会 present 失败——出现即回退)。

### 第二步:做成 SukiSU 模块(验证通过后)

模块目录结构:

```
sf_fp16_client_target/
├── module.prop
├── system.prop
└── service.sh            (可选兜底,见下)
```

`module.prop`:

```
id=sf_fp16_client_target
name=SurfaceFlinger FP16 Client Target
version=1.0
versionCode=1
author=Lenovo-Tab-UltraHDR-Fix
description=开启 SurfaceFlinger fp16_client_target(debug.sf.fp16_client_target=true),使 HDR 客户端合成走 FP16 并让 displayRatio 参与亮度映射,修复高光钳白
```

`system.prop`(核心,一行):

```
debug.sf.fp16_client_target=true
```

`service.sh`(可选兜底:万一 ksud 的 system.prop 时序异常,在启动完成后强制设置并重启 SF;正常情况不需要):

```sh
#!/system/bin/sh
MODDIR=${0%/*}
until [ "$(getprop sys.boot_completed)" = "1" ]; do sleep 2; done
if [ "$(getprop debug.sf.fp16_client_target)" != "true" ]; then
  resetprop debug.sf.fp16_client_target true
  killall surfaceflinger   # init 自动重启 SF
fi
```

> 注意:sf_fp16 是普通 debug prop(非 persist、非 ro),`system.prop` + 重启即为干净方案;service.sh 属保险丝,不建议默认启用(重启 SF 有短暂黑屏)。

### 风险与回退

| 风险 | 评估 | 处置 |
|---|---|---|
| HWC 拒绝 FP16 client target(花屏/黑屏) | 低-中(QTI composer + Adreno 通常支持 FP16 渲染;但本机 HWC 上报能力未验证) | 卸载模块或 `resetprop --delete debug.sf.fp16_client_target` 后重启 SF |
| GPU 带宽/功耗上升(FP16 合成是 8888 两倍字节) | 中:仅 GPU 合成帧(client composition)受影响,正常画面多为 HWC overlay 不走此路径 | 观察;不合适即回退 |
| 与 4 前提中其他缺失项叠加,收益不足 | 未知:flag 只是前提之一 | 逐前提验证,flag 打开后重测 displayRatio 是否参与 |
| OTA | 无:不修改任何分区文件 | 模块天然 OTA 安全 |
| 未来固件移除 prop 通道 | 低(AOSP main 仍保留该宏) | 届时转 patch 二进制方案(§4/§5) |

## 4. 备用方案:patch surfaceflinger(仅当 prop 通道在未来版本失效时)

方法论(已在本次调查中把 366 的地址全找好):

1. 定位 flag 读取函数:strings 找 `"debug.sf.fp16_client_target"`(file_off 0x51684,vaddr 同 0x51684,LOAD 段 0 偏移映射);
2. 扫 ADRP+ADD 组合(ADRP 页 0x51000 + ADD #0x684)得引用 0x7009a4 → 函数头 0x700904(即 FlagManager::fp16_client_target);
3. patch 选择(任一):
   - 最小化:0x7009a4 处把 `add x1, x1, #0x684` 的 imm12 改 0(prop 名为空串 → GetBoolProperty 返回 nullopt → 不生效,**不可行**,放弃此思路);
   - **推荐**:在函数入口 0x700904 直接 `mov w0, #1; ret`(8 字节:`20 00 80 52 C0 03 5F D6`)—— 函数恒返 true,等效于 prop 恒 true;
   - 或改消费点 0x2fce9c `tbz w0,#0`(b.eq→nop):粒度更细但点位多。
4. KSU 模块 magic mount 替换 `/system/bin/surfaceflinger`(需同时放 rc 文件否则 init 可能校验;本机 366 已提取 `system_a__366__surfaceflinger.rc`);
5. 风险:vboot/OTA 完整性对 system 分区文件 + mount 方式的校验(部分设备 avb 验证 system 內部文件哈希的概率低,但要实测);每次 OTA 需用新固件二进制重做 patch。

**366 上无需走这条路**——prop 即官方后门。

## 5. 替代思路评估(如果实测 flag 打开后收益不足)

- **PQ tone map 开关**:SF/RenderEngine 没有"GPU 合成改 PQ tone map"的独立 prop;亮度映射正是消费点 1 那个比率函数在做,flag 打开后它才参与 —— 即本路径本身就是 tone map 正道。
- **Graphite/Vulkan RenderEngine**:`debug.renderengine.graphite=true`、`debug.renderengine.vulkan=true`(二进制中存在)可与 fp16 组合测试不同 GPU 合成后端对 FP16 渲染的兼容性/画质。
- **persist.sys.sf.native_mode=257**(366 build.prop 已有):色域模式相关,与本问题正交,不动。
- **LSPosed**:确证无法触及(纯 native 侧 static 缓存,Java hook 无插桩点)。
