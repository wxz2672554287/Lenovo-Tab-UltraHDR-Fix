## 1. getFloat 新实现（重点审）

### 1.1 AOSP 存在性（独立网络核实，非引用仓库结论）

抓取 AOSP googlesource 两个版本全文核对：

| 版本 | `get(String)` | `get(String,String)` | `getInt` | `getLong` | `getBoolean` | `getFloat` |
|------|----|----|----|----|----|----|
| main（refs/heads/main） | ✓ | ✓ public static @SystemApi | ✓ | ✓ | ✓ | **不存在** |
| android-9.0.0_r1 | ✓ | ✓ public static @SystemApi | ✓ | ✓ | ✓ | **不存在** |

→ v2.0.10 修复的前提（"getFloat 从不存在，旧反射 NoSuchMethodException 被静默吞，死代码从 v1.x 活到现在"）**成立**；新反射目标 `get(String,String)` **存在且可反射**。

### 1.2 反射签名精确匹配问题

`getMethod("get", String.class, String.class)` 按**参数个数+类型精确匹配**，只会命中两参重载 `get(String,String)`，**不可能**匹配到 `get(String)`（参数个数不同，getMethod 无隐式重载解析）。✓ 无歧义。

### 1.3 parseFloat 行为边界（实测验证）

| 输入 | 行为 | 后果 |
|------|------|------|
| prop 未设置/为空 | `native_get` 直接返回 def（AOSP javadoc："not set **or empty**"），`Float.toString(0f)="0.0"` 往返无损 | 返回 def，无异常路径 ✓ |
| `"1.3"` | 1.3f | ✓（App 侧 ControlsPage `MAX_OPTIONS = ["0","1.2","1.5","2.0","2.5","4.0","8.0"]` 全为规范十进制，写入格式兼容） |
| `"0"` | 0.0f | ✓（0>1.0f false → 不钳制，语义=不限） |
| 带空白 | `v.trim()` 处理 | ✓ |
| `"NaN"` | Float.NaN | `userMax>1.0f` 恒 false → 不钳制，与默认 0 等效，**安全** ✓ |
| 垃圾值 `"abc"` | NumberFormatException | → `logAlways("BAD VALUE")` + 返回 def，**不再静默** ✓ |
| `"Infinity"` | Float.POSITIVE_INFINITY | `ratio > Infinity` 恒 false → 不钳制（用户显式设置的极端值，可接受） |

### 1.4 logAlways 早期调用安全性

- getFloat 的 catch 调 logAlways，但 getFloat **首次被调是在 HOOK4 回调运行期**（system_server 完全运行后），不在类加载阶段；
- handleLoadPackage 起始的 logAlways("loaded v...")：XposedBridge.log 在 system_server 中由 LSPosed 重定向，安全；FileLog.write 全程 try/catch 包裹（含 /data/system 不可建文件场景→FileNotFoundException 被吞→diagFailedOnce 一次性告警），**不可能向外抛异常**；
- FileLog 依赖的 SimpleDateFormat/FileWriter 均为 boot classpath 标准类。✓

### 1.5 验收场景可达性（数学验证）

`persist.sys.tb710.hdrfix.max=1.3` 时（parseFloat("1.3")=1.3）：全段 4→800nits **0 违例点，实际峰值 ratio=1.3000**（此前 v2.0.9 该钳制为死代码、实测写 1.9757）。userMax=1.05/2.0 同样精确钳制。**修复有效。**

## 2. PEAK 750 连锁 — 数学验证输出（python 全域重算）

公式：模块 `ratio = max(min(interp(spline, sdr), 750/sdr), 1.0)`（userMax 生效时再钳）；DPC 实际抬亮 `min(spline(sdr), desired=5) × sdr` 后 clamp 800。

```
== A. 全域对比（模块750 vs DPC clamp800）==
  sdrNits   module750       dpc     diff    diff%   方向
       4      4.0000      4.0000  +0.0000  +0.00%  EXACT
      75      3.9950      3.9950  +0.0000  +0.00%  EXACT
     150      2.5253      2.5253  +0.0000  +0.00%  EXACT
     300      1.7892      1.7892  +0.0000  +0.00%  EXACT
     480      1.5621      1.5621  +0.0000  +0.00%  EXACT   ← 750 cap 首个介入点 sdr≈480.1
     490      1.5306      1.5729  -0.0423  -2.69%  UNDER(欠曝/安全)
     502      1.4940      1.5848  -0.0908  -5.73%  UNDER
     542      1.3838      1.4760  -0.0923  -6.25%  UNDER
     600      1.2500      1.3333  -0.0833  -6.25%  UNDER
     700      1.0714      1.1429  -0.0714  -6.25%  UNDER
     750      1.0000      1.0667  -0.0667  -6.25%  UNDER
     800      1.0000      1.0000  +0.0000  +0.00%  EXACT（双双触底 1.0）
分界：4→480.1nits 偏差 0.0000；480.1→800nits 全部 UNDER；OVER 点 = 0 个

== B. 高段恒定比 ==  sdr>502 后 module/dpc ≡ 750/800 = 0.937500（实测 0.937500）

== E. 事件频率 ==  4→800nits 全扫(0.5步, 阈 0.005)：410 次（v2.0.8 PEAK=800 基线 422），仍低频

== G. 高段绝对 HDR 白点 ==
  sdrNits    模块标称白   DPC实际白   标称/实际
     300        536.8       536.8     1.0000
     470        729.0       729.0     1.0000
     500        750.0       791.4     0.9477
     542        750.0       800.0     0.9375
     700        750.0       800.0     0.9375
```

### 定性分析：物理诚实 vs 不同步

- **750 是有意的、且是与 KSU 修复协同的正确选择。** 800 clamp 来自 displayconfig 软件标称峰值，而 EDID/HWC `mMaxLuminance=750` 是 SF/HWC 视角的**物理上限**。在 `debug.sf.fp16_client_target=true` 落地后，模块写的 ratio 正式参与 SF 的 HDR 编码——此时若仍写 `800/sdr`（标称白点最高 800 > HWC 认为的 750），等于要求 SF 编码一个物理上不存在的白点，**方向上恰好复现"高光被钳白"的老问题**；写 `750/sdr` 使标称白点恒 ≤ SF 认为的物理上限，编码闭环诚实。
- **代价与方向**：高段（>480nits）HDR 高光比"DPC 抬亮理想同步"保守 ~6.25%（756 vs 800 标称差中面板实际可持续输出取 750）。欠曝方向 = 高光略暗一点，**绝无过曝/钳白风险**。安全侧偏差，且 v2.0.9 实测诊断（main=755nits 实抬）支持 750 更接近物理真值。
- **同步性**：4→480nits 主流使用区间（常用亮度全段）与 DPC 抬亮**逐点 0.0000 偏差**，不同步仅存在于高段尾部的 6.25% 保守差。

## 4. 与 KSU fp16 模块组合交互

- 模块侧 SysProps.set 仅写 `persist.sys.tb710.hdrfix.hooked/version`（L126-127），**不写也不覆盖 `debug.sf.fp16_client_target`**；KSU system.prop 在 post-fs-data（SF 启动前）设置，两模块作用域无交集，无覆盖竞争。
- fp16=true 后 SF 消费 ratio 参与 HDR 编码：模块持续写 `mCurrentHdrSdrRatio` + `info.hdrSdrRatio` + EVENT（消费链已被视频对照实证正常），模块代码中**无任何以 fp16=false 为前提的逻辑分支**，无自相矛盾。
- `forceGpuComposition`（tx1008 强制 GPU 合成）与 fp16 client target **互补而非冲突**：GPU 合成下 client target 由 RE 输出，fp16 使其为 FP16 格式，8bit 钳白路径不存在。
