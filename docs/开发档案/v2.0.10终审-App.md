## 一、多余功能清单（用户点名逐项裁决）

### 1. 检查更新 + GitHub 仓库入口（AboutPage.kt）——【删/改】
双重死因：
- **AndroidManifest.xml 无任何 `uses-permission`**，包括 INTERNET。`AboutPage.checkUpdate()` 的 `HttpURLConnection` 在无权限下必然抛异常 → 永远走 `update_failed`（"检查更新失败（网络？）"），把责任甩给不存在的网络问题。已核实合并清单仅含 `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`，依赖库（compose/miuix/core-ktx）不带 INTERNET。该功能自始至终没成功过。
- 仓库 `wxz2672554287/Lenovo-Tab-UltraHDR-Fix` 已转 private：即便补上权限，`releases/latest` API 也返回 404；"GitHub 仓库"入口点开也是 404。

**建议**：删掉"检查更新"按钮 + `semverNewer()` + `GITHUB_REPO` + 相关 URL 代码（连带消解致命 bug F1）；"GitHub 仓库"行删掉或改文案为"源码暂不公开"。同时省掉 INTERNET 权限声明（App 更干净，符合"日志控制台"定位）。

### 2. `Props.DEBUGFILE` 死开关残留（Shell.kt:164）——【删】
`const val DEBUGFILE = "persist.sys.tb710.hdrfix.debugfile"` 全仓库唯一出现处即定义本身：HdrRatioFix.java 无对应 `PROP_DEBUGFILE`，UI 无引用，模块从不读。v1.x 遗留。删除零风险。

### 3. 九条死字符串（双语各 9 条）——【删】
全部 0 处代码引用：
- `status_channel` / `channel_primary` / `channel_fallback` / `channel_unknown` —— v1.x"比率来源"功能的残留；
- `test_caps`、`requires_root` —— 无对应 UI；
- `confirm_disable_title` / `confirm` / `cancel` —— 原确认对话框方案被 `disableArmed` 两次点击机制取代后残留（该机制自身问题见 W4）。

### 4. mode 2（v1.1.8 旧版对照）——【UI 收起，模块代码保留】
用户问"还需不需要"。v2.0.7 定案后其实质性差异已萎缩：
- HOOK 2 `hasSpline 强制 false`：运行时 hasSpline 本来就是 false（366 加载链没把 vendor map 送进 HBMData）→ **无操作**；
- HOOK 1 `handle 短路`：handle 本来就永不被调 → **无操作**；
- 真正剩下的差异只有一点：F 写口用 `mCurrentNits`（被抬亮污染的主通道）而非 SDR 通道算 ratio —— 即"复现已知错误值"的路径。

结论：作为"复现旧 bug"的 A/B 对照价值仅剩一条失真曲线；日常使用必然误导（值偏高/钳 1）。**建议**：ControlsPage 下拉去掉 mode 2 项（0/1 两档），模块端 `legacyWrite`/HOOK1/HOOK2 代码保留不删（一个 if 的事，删核心路径收益低风险高；OTA 后若 handle 复活仍有观察价值）。若坚持保留下拉，至少把 summary 中"comparison only"加强为"已知失真，勿日常使用"。

### 5. mode 1（禁抬亮）——【留】
与 fp16 方案正交：fp16 prop 修的是 SF 渲染链高光钳白（8bit client target → FP16）；mode 1 修的是 HdrBrightnessModifier 面板物理抬亮拖亮 SDR UI。fp16 落地后若 SDR 内容不再被拖亮，mode 1 平时用不上，但它是**过曝/拖亮的唯一用户侧逃生门**，且 hook 无条件安装、动态生效、无回退成本。**建议保留**，可在 summary 加一句"fp16 方案后通常无需开启"。

### 6. GPU 合成开关——【留，但状态显示语义要改】
修的是 DPU tone-mapping 闪屏，与 fp16（高光钳白）是两个独立问题。用户现在还开着——**建议实测**：fp16 生效后关闭 GPU 合成，若闪屏不复发则关掉省电（GPU 合成有持续功耗代价）。

App 侧两个小毛病：
- StatusPage 的"Force GPU composition: On/Off"读的是 prop 值，但 prop 只在**下次开机**才被模块消费（system.prop 时序 + 开机 15s 延迟执行一次），显示"On"不代表本次开机已强制。建议 summary 注明"重启后生效"（ControlsPage 文案已有，状态页没有）。
- 该开关与 fp16 同属 KSU 模块职责边界：GPU 合成仍由 LSPosed 模块开机线程执行（HdrRatioFix.java:463-474），继续留在 App 开关里合理。

### 7. max 上限下拉含 "8.0" 档（ControlsPage.kt:29）——【删 8.0 档】
用户问"UI 值与模块语义是否匹配"。数值语义匹配 ✓：getFloat 修复后 `userMax > 1.0f` 才钳制，"0"=不限制与模块 `getFloat(PROP_MAX, 0f)` 默认一致，UI 显示 unset→"不限制"正确。**但选项范围虚高**：模块写入值恒 ≤ min(spline 上限 4.0（4nits 处），750/sdrNits)，即 **ratio 永远不可能超过 4.0**——设 "8.0" 纯属无效值，"4.0" 也只在 sdrNits≤4（屏幕接近熄灭）才可能触顶。**建议**：`MAX_OPTIONS` 改为 `0 / 1.2 / 1.5 / 2.0 / 2.5 / 3.0 / 4.0`（删 8.0），文案可注"实际上限 4.0（OEM 曲线封顶）"。

### 8. 旧 `ksu-module/`（displayconfig 方案）目录——【归档，明确禁用】
仓库层面并存两套 KSU 模块：旧 `ksu-module`（overlay displayconfig 恢复 sdrHdrRatioMap，9 月 1 日方案）与新 `ksu-fp16-module`（最终方案）。**风险**：若设备上旧模块仍启用，sdrHdrRatioMap 恢复 → hasSpline 变 true → 系统 handle 复活写入 → 推翻 v2.0.7 "模块是 mCurrentHdrSdrRatio 唯一活写入者"的核心假设，引入双写竞争。**建议**：README/打包说明明确"只刷 fp16 模块，必须禁用/卸载旧 displayconfig 模块"，或将旧目录移入 `docs/` 归档。

### 9. `xposed_description`（中英双语，strings.xml:4）——【改文案】
仍是 v1.x 语义："legacy HWC 缺 SurfaceControl 亮度能力 → 强制 NaN" 与 v2.0.7 定案（hasSpline 运行时 false）不符；未提三模式/fp16 组合；LSPosed 管理器里用户看到的模块说明会误导。"不触碰任何亮度路径"的免责表述在 mode 1（短路 HdrBrightnessModifier.apply）语境下也需要更精确（"不写入亮度/背光值"）。发版前顺手更新。

### 10. 测试页浏览器入口（zyyme.com）——【可留】
外部第三方链接，死活不可控但轻量、是 HDR 视频测试唯一方便入口（WebView 按平台设计不渲染 HDR，文案已说明）。保留可接受；追求极致精简可删。

## 三、KSU 模块组合交互核查（service.sh ↔ App）

| 交互点 | 结论 |
|--------|------|

| 路径显示 | LogsPage `logPath` 恒显示 `/data/system/hdrfix.log`（service.sh 保证存在、B3 语义 FALLBACK 优先）——与实际写入者（模块 FileLog PATHS[0]）一致 ✓。StatusPage root 行文案"日志目录保持在 /storage/emulated/0/hdr日志/"与活跃日志实际在 /data/system 有轻微认知差（sdcard 只是常驻镜像），可接受。 |
| system.prop（fp16） | `debug.sf.fp16_client_target=true` 纯 SF 侧 prop，与 App 无交互；App 状态页未展示 fp16 状态（可考虑在关于页加一行"fp16 KSU 模块版本"提示，非必需）。 |
| **旧模块残留风险** | 见多余功能第 8 条：旧 ksu-module（displayconfig）若同时启用会破坏"唯一写入者"假设，发帖/打包说明必须写明互斥。 |
