## 2. 机制定案(浓缩版;完整推理见 `反编译证据/机制笔记-完整版.md`)

### 为什么 A15 好好的、A16 坏了 —— 三个断点

1. **比率数字链断**(出厂"不提亮"的直接原因):A16 QPR 把 `sdrToHdrRatioSpline` 从顶层字段迁进重构后的 `HighBrightnessModeData`;联想的私有加载器 `zuiLoadHighBrightnessModeData`(读 `/system/etc/display_hdr.xml`)只填新字段 `mHdrBrightnessData`,而 A16 的 `hasSdrToHdrRatioSpline()` 读 `mHbmData.sdrToHdrRatioSpline`——**运行时恒 null → 恒 false → `handleHdrSdrNitsChanged` 永不被调 → ratio 恒 NaN → App 窗口降级,图片永远 SDR**。(注意:vendor XML 里其实有 `sdrHdrRatioMap`,解析器代码也还在读同名元素——**静态看链路是通的,但运行时实测是断的**。别再犯"静态推断当运行时结论"的错,这是本项目最大的一个坑。)
2. **合成端钳白**(强开提亮后"过曝"的根因):SF 的 aconfig flag `fp16_client_target` 编译期为 false 时,`Output::getHdrSdrRatio` 恒返 1.0——displayRatio 不参与 RenderEngine 对 8bit client target 的 HDR 编码,FP16 gainmap 层的高光被压平堆积在顶格=死白。**过曝程度∝ratio**(低亮度 ratio≈1.98 严重、高亮度→1.0 轻),这个"亮度反转"形态是它的指纹。
3. **DPU 合成异常**(闪屏):老 QTI HWC 对 A16 gainmap 层的 device 合成路径异常,强制 GPU 合成(SF tx1008)即消。

### 为什么 HDR 视频一直是正常的(对照实锤,定案关键)

视频层(YUV 10bit + BT2020_HLG dataspace)走 HLG/Libtonemap 通道:SF 把我们写入的 ratio 正确用于白点下发(实测 HDR 白=SDR背光×ratio,SDR UI 按 1/ratio 压暗),tone map 保留高光细节。**同一个比率,视频链工作完美**——这证明比率写入链是对的,断点只在 FP16 EXTENDED 层的渲染通道(fp16_client_target)。诊断时找"同机制下正常工作的路径"做对照,是最有力的定位手段。

### 修复侧的关键事实

- `debug.sf.fp16_client_target=true` 经 `su 0 sh -c "setprop ... && stop && start"` 软重启生效,**实机验证消除过曝**;它是 SF 的 FlagManager prop 覆盖通道(AOSP 源码宏+366 二进制反汇编双证,prop 无条件覆盖编译值,即使 fixed_read_only)
- **`debug.` 前缀的 prop 不持久,重启即丢**——永久化只能靠 KSU 模块的 `system.prop`(ksud 在 post-fs-data 设置,早于 class core 的 SF,官方文档证实时序)
- LSPosed 模块的核心:hook `getDisplayDeviceInfoLocked` after,用 `setDisplayBrightness` 双参数(经系统自己的 `brightnessToBacklight`/`backlightToNits` 换算)算出 **A15 真除式 ratio = main/sdr**,值变化≥0.005 时写 `mCurrentHdrSdrRatio` + 在 syncRoot 内调 `updateDeviceInfoLocked()` 发事件(事件是 App 三层缓存刷新的唯一途径)
- 数学自洽:DPC 抬亮=SDR×min(spline30(SDR), desired)且 clamp 物理上限,我们写的 ratio 与之逐点一致(全域偏差 0;高段按 EDID 750 而非软件标称 800 封顶,保守约 6%,安全侧)

## 3. 踩坑总清单(按类别;每条都是真金白银换的)

### 3.1 机制认知坑(修改系统行为前先读)

| # | 坑 | 教训 |
|---|---|---|
| M1 | 静态推断 `hasSpline=true`(XML 有数据+解析器读同名元素),运行时实测 false | **静态分析只能提出假设,定案必须运行时证据**(logcat/dumpsys/设备实测) |
| M2 | v1.1.7 短路系统 handle,以为在修"竞争写入者",实际砍死了唯一的真值源 | 动别人的代码前,先确认它在运行时**真的在跑** |
| M3 | App 的 DisplayInfo 是三层事件驱动缓存(DMS/LogicalDisplay/App进程),只改"当次查询返回值"缓存永远不刷 | 改数据必须走**事件链**(`updateDeviceInfoLocked` → EVENT_DEVICE_INFO_ADJUSTED) |
| M4 | system_server 写不了 /storage(AOSP SELinux neverallow 明文,2016 年立规) | 别试图让注入进程直写用户存储;root 预建文件也没用(neverallow 是域级) |
| M5 | system_server 在 /data/system 也**无权新建**文件(只能 append 已存在的) | 日志文件必须 root 预建(KSU service.sh)+chown system+chmod 666 |
| M6 | 删除被打开的文件后,O_APPEND 写入进孤儿 inode,不报错,日志静默停写 | 清日志用 **truncate 原地清空**,永远不要 rm 活文件 |
| M7 | `debug.` prop 非持久,手动 setprop+reboot 后 prop 已丢,"无效果" | 测试用软重启(一条命令!);永久化走 KSU system.prop |
| M8 | "让位系统真值"的逻辑写好后,系统真值从未到来(handle 死的)→ 字段冻结 | 让位逻辑的前提是**确认**有别的写入者活着 |
| M9 | A15 的"渐进观感"来自 ratio 跟随面板 ramp 逐帧爬升,写终值(spline)会变成"卡一下突然跳变" | 复刻行为要复刻**过程**不只复刻终值 |
| M10 | 过曝∝ratio、高亮最轻的"亮度反转"形态,是 8bit client target 钳白的指纹 | 症状形态可以做定位指纹 |

## 4. 关键数字与公式速查(本机实测)

```
面板:物理 750nits(EDID mMaxLuminance;软件标称 800,勿信)
OEM 抬亮曲线 spline30(30 点):4nits→4.0 ... 500→1.585, 502.2→1.593(最高 4.0)
DPC 抬亮 = SDRnits × min(spline30(SDRnits), SF desired)  [desired=图片增益容量,实测 5.0]
       再 clamp 到物理上限
正确 ratio(A15 真除式)= 实测 main / sdr 两个亮度通道的商
  - 静止/无 HDR 时 = 1;抬亮收敛后 = spline30(SDR);动画期逐帧渐进
16 点亮度→nits 映射:0.0→7.95 ... 1.0→800(dumpsys display 的 mBrightnessToNitsSpline)
实测采样(76/255 档):SDR=239nits,面板抬到 473,sysfs 背光 2414/4095 逐一吻合
```

诊断命令速查(设备 SSH/root):
```sh
su -c "dumpsys SurfaceFlinger" | grep -a -iE "fp16|default-format|whitePoint|dimming|numHdrLayers|desiredRatio"
su -c "dumpsys display" | grep -a -iE "hdrSdrRatio|sdrToHdrRatioSpline|BrightnessEvent"
su -c "logcat -d -v time" | grep -a HDRRatioFix        # 模块日志(100% 可靠通道)
cat /sys/class/backlight/panel0-backlight/brightness    # 物理背光电平(0-4095)
```
